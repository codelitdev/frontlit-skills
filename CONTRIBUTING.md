# Contributing

Notes for people maintaining these skills. Users only need the [README](README.md).

## How the skills route website changes

A standalone `SKILL.md` is portable workflow guidance, not a universal MCP installer. The `frontlit` plugin packages the connection alongside its skills for Claude Code and Codex. Other plugin-capable hosts need their own supported manifest/configuration; ordinary skill installation should not be assumed to load plugin-level `.mcp.json`. Codex also supports MCP dependency declarations in `agents/openai.yaml`; these skills do not declare MCP as a required dependency because their Git workflows work without it.

| Change | Source |
| --- | --- |
| Website name, subtitle or logo | FrontLit branding: `get_team_settings` / `update_team_settings`, even when pages are Git-managed |
| One page's SEO title or description | Page JSON in Git, or builder SEO / MCP `update_page` for builder-owned pages |
| A page's visible heading | The hero block title |
| Git-managed header, footer, theme or redirects | `site.json` |

For example, “Set the site title to John's Piping Pizza” updates branding through `update_team_settings({"title": "John's Piping Pizza"})`; changing the homepage SEO title alone does not complete that request. If MCP is unavailable, the skills point to **Website → Branding → Site title** and report that operation as pending.

## Keeping in sync

- **frontlit-docs:** `references/format.md`, `references/porting.md` and `scripts/check.mjs` mirror FrontLit's docs parser and validator (`packages/text-editor/schema/content.v1.json` lists every rich block and its props; the rules behind it are in `packages/text-editor/src/core/library/` (`text-blocks.ts`, `links.ts`), `src/docs/` (`profile.ts`, `blocks.ts`, `frontmatter.ts`, `urls.ts`) and `src/core/urls.ts`) and the OpenAPI import (`docs/openapi-support.md`, `apps/api/src/documentation/openapi/`). `scripts/openapi.mjs` mirrors `apps/api/src/documentation/openapi/import.ts` (blocking rules, warnings, slugs and routes); `scripts/redirects.mjs` mirrors the redirect-domain rules in `packages/api-contract/src/schemas/domains.ts` and `apps/sites/lib/host.ts` (`redirectDomainTarget`). Update them whenever those rules change in the FrontLit repository, and run the scripts' `*.test.mjs` files. To run `check.test.mjs` against an unreleased parser, build `packages/text-editor` in a FrontLit checkout and set `FRONTLIT_PARSER_DIR` to that folder. MediaLit's `frontlit/docs` folder (`node check.mjs <folder> --api-mount=api`) is a good real-world check.
- **frontlit-pages:** `scripts/schema/page.v1.json` and `site.v1.json` are copies of `packages/page-builder/schema/` in the FrontLit repository (generated by `bun run schema:generate` there). Copy them again whenever block settings change (`scripts/check-schema-sync.mjs` compares them with the published `https://frontlit.app/schema/page.v1.json` and `site.v1.json`; CI runs it on every pull request and daily, so drift fails a check instead of going unnoticed), then, from `plugins/frontlit/skills/frontlit-pages/examples`, run `node ../scripts/check.mjs frontlit/pages --fix` (the examples must stay valid and canonical) and update `references/blocks.md`. The import rules in `scripts/check.mjs` and `references/format.md` (file names, reserved routes, content feeds, link and image checks) mirror `apps/api/src/pages/git-import.ts`, and its block rich-text limits (`pageTextProblems`: no tables, images or headings outside `##` to `####`) mirror `pageTextProfile` in `packages/page-builder/src/schema/rich-text.ts`.
- **frontlit-pages backgrounds:** `references/background-presets.json` is exported from FrontLit's `packages/page-builder/src/builder/controls/pattern-presets.ts` (the builder's Pattern presets). Re-export it when presets change.
- **frontlit-pages embeds:** `references/embeds.md` and `scripts/test-embed.mjs` mirror FrontLit's `packages/page-builder/src/components/inline-embed.tsx` (`prepareEmbed`, script handling); update them when that file changes.
- **frontlit-support:** the API, fields and snippet live in FrontLit's `frontlit/docs/developers/in-app-support.md`; the skill links to it instead of copying it. Keep the rules in `SKILL.md`, the request shape in `references/recipes.md` and the tools in `references/mcp.md` in line with `apps/api/src/support/` (`POST /support-sessions`), `packages/api-contract/src/schemas/` (support session body, 8 KB context limit) and the `create_api_key` / `create_support_session` / chatbot tools in `apps/api/src/mcp/tools/`. `examples/in-app-support` in the FrontLit repository is a working host app to compare against.
- **frontlit-articles:** `references/mcp.md` follows the shared document tools in FrontLit `apps/api/src/mcp/tools/documents.ts` and `media.ts`. The slug section of `SKILL.md` and the "Known issues" (links rendered with `target="_blank"`/`nofollow`, `featuredImage.mediaId` stored as `mediaLitId`) describe current server behavior; update them when FrontLit adds an article slug field or fixes those issues.
- **MCP routing:** `references/mcp.md` in each skill follows FrontLit `apps/api/src/mcp/tools/` and `packages/api-contract/src/schemas/`. Refresh tool names, input examples, ownership fields and scope guidance when those contracts change. Branding uses flat team settings fields; `website.branding.title` describes the product concept, not the MCP argument shape. The deployed tool schema remains authoritative.
- **Plugin connections:** `plugins/frontlit/.mcp.json` must use the remote endpoint documented in FrontLit `apps/docs/content/docs/developers/mcp.mdx`. Keep them free of credentials and bump the version in `plugins/frontlit/.claude-plugin/plugin.json` when shipping skill/config updates.

Packaging references: [Claude plugin MCP configuration](https://code.claude.com/docs/en/mcp#plugin-provided-mcp-servers), [OpenAI skills and MCP](https://developers.openai.com/plugins/build/skills), and [OpenAI plugin packaging](https://developers.openai.com/plugins/build/plugins).
